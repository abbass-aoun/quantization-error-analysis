Hi everyone. My project asks a simple question: when we compress a model with a smarter method like GPTQ, does it only make fewer mistakes, or different kinds of mistakes? I compare GPTQ with plain round-to-nearest, RTN, on exactly the same 4-bit grid, so the only difference is GPTQ's error correction. I test Qwen2.5-1.5B on math reasoning (GSM8K) and factual recall (TriviaQA). The graphic on the right is the core operation: every weight, the hollow dot, snaps to one of 16 levels.

Motivation2
Why quantize at all? A 175-billion-parameter model needs 326 gigabytes just to hold its 16-bit weights, about four high-end GPUs. Storing each weight in 4 bits needs about a quarter of that memory. And text is generated several times faster, because generation spends most of its time reading weights from memory; GPTQ measured 3.25 times on an A100 for 3-bit OPT-175B. The catch is on the right. This is a schematic: ten questions, seven right before and seven right after quantization, so accuracy says nothing changed. But four answers flipped: two right to wrong, two wrong to right. Dutta et al. measured this on real models: accuracy within about two percent while up to 13.6 percent of answers flip. So my question: when answers break, how do they break, and does GPTQ change that compared with RTN?

RTN: snap each weight alone

No data and no interaction: errors in the same direction add up in the layer's output. Each group of g = 128 weights gets its own s and z (≈0.15 extra bits per weight).

Method · uniform asymmetric grid, as in Lecture 115
First, the grid, the same equations as Lecture 11. Step one: from a group's minimum and maximum we get the step size s and the zero-point z. Step two: each weight w becomes an integer code q between 0 and 15 at 4 bits; that integer is what is stored. Step three: at inference we use w-hat equals s times q minus z. A worked example: a group from minus 0.5 to 0.7 at 4 bits gives s = 0.08 and z = 6; the weight 0.23 becomes q = 9 and is used as 0.24. RTN does this for every weight on its own, with no data. Errors pointing the same way simply add up in the output. Every group of 128 weights has its own s and z, which costs about 0.15 extra bits per weight. RTN and GPTQ in my project use exactly this grid.

Method · Optimal Brain Quantization idea · live demo6
GPTQ's objective is the layer's output, not its weights: keep W-hat X close to W X on calibration inputs. For each row this is a quadratic problem with Hessian H = 2 X X-transpose, which tells us which input features move together. The update, from Optimal Brain Quantization: after rounding column q, add a correction delta to the remaining columns, proportional to the rounding error divided by the diagonal of H-inverse. The two-weight example is verified numerically. Both weights are 0.4, the grid is 0 and 1, the inputs are strongly correlated. RTN rounds both to 0: output error 1.216. GPTQ rounds the first to 0, pushes its error into the second, which moves to 0.76 and rounds to 1: output error 0.176, seven times lower and the best possible grid choice. [Open the simulator, about 90 seconds.] Press Round next column a few times: the yellow column is rounded, the cyan columns absorb its error. Watch the two error curves: GPTQ stays low. Then drop the correlation slider: GPTQ's advantage disappears. That connects to my Qwen result later.
Method · 3 / 3 · algorithm & cost

Three changes that make OBQ scale

Algorithm 1 · GPTQ (one layer)
input: W (drow×dcol), H = 2XX⊤, block B = 128
H ← H + λI            # λ = 1% of mean diag
U ← Cholesky(H-1)⊤       # upper triangular
for i = 0, B, 2B, …:     # blocks of columns
  for j = i … i+B−1:      # same order, all rows
    Q[:,j] ← quant(W[:,j])
    E[:,j] ← (W[:,j] − Q[:,j]) / U[j,j]
    W[:,j:i+B] −= E[:,j] · U[j, j:i+B]
  W[:,i+B:] −= E · U[i:i+B, i+B:]   # lazy
return Q
1

One fixed column order

all rows share it, so H⁻¹ is updated once per column, not once per weight

2

Lazy batches of 128 columns

far columns are updated once per block, so the GPU computes instead of waiting on memory

3

Cholesky + 1% damping

the needed rows of H⁻¹ are computed once and stay numerically stable in huge layers

Cost per layer [2]

OBQ → GPTQ

Measured here · one T4

Qwen2.5-1.5B: RTN 2.4 min, GPTQ ≈15 min per model

Memory

one dcol×dcol Hessian per layer: 9 MB (attention) to 321 MB (MLP)

Method · blocks processed in order, each on already-quantized inputs7
This is Algorithm 1, which I re-implemented in PyTorch. Add 1% damping to H, take the Cholesky factor of its inverse, then sweep columns in blocks of 128: quantize a column, scale its error by the Cholesky diagonal, subtract it from the remaining columns of the block, and update far columns once per block. Three changes make this scale: one column order for all rows, so H-inverse is shared; lazy batches, so the GPU computes instead of waiting on memory; and Cholesky with damping for stability. Cost: OBQ is d-row times d-col cubed per layer; GPTQ is the max of d-row d-col squared and d-col cubed. On one free T4, RTN took about 2.4 minutes and GPTQ about 15 minutes per Qwen model, including evaluation and saving. Memory: one Hessian per layer, from 9 MB for attention to 321 MB for the MLP down projection, because it grows with the input width squared.

Experimental Protocol · 1 / 2

What counts as a flip

Same question, asked to the original model and to a quantized one. If correctness changes, it is a flip.

Right or wrong is decided by rules

Math: the number in \boxed{}, compared as a number (11/2 counts as 5.5).
Facts: any accepted answer, ignoring case, accents and "the".

Protocol · greedy decoding, no repetition penalty, identical prompts · the examples are made up to explain the labels9
A flip is the same question, asked to the original model and to a quantized one, where correctness changes. Right before and wrong after is a harmful flip; these are the ones I classify. Wrong before and right after is a repair flip, which I count. Right or wrong is decided by rules, not by an AI: for math, the number in the box compared numerically, so 11 over 2 equals 5.5; for facts, any accepted answer after normalization. Two illustrative examples, made up to explain the labels, not results. Math: the original model halves 48 correctly and answers 72; a quantized model halves it to 12 and answers 60. The plan was right, the arithmetic was wrong, so it is an execution error. Facts: the original says Gorky; a quantized model says Kirov, another Soviet-era city name, so it is a near-miss rather than an unrelated answer.

Protocol · confidence = mean and lowest token log-probability of the original model's answer10
Each harmful flip gets one error type. For math I adapt Li et al.'s categories and add degeneration: loops or no answer, conceptual: misreading the problem, method: the wrong plan or formula, execution: an arithmetic slip, and reasoning: steps that don't follow. For facts: degeneration, no answer, near-miss: a related but wrong entity, and unrelated. Labels come in three layers: rules first for loops and missing answers; then one LLM judge, deliberately not a Qwen model, with fixed definitions; then I hand-label a random sample and report agreement as Cohen's kappa. What I test: RQ1, how many answers flip, with McNemar; RQ2, whether RTN and GPTQ produce different error types, with chi-square; RQ3, whether the original model's confidence predicts which answers flip and what they become, with AUROC; plus whether math calibration helps math but hurts facts.

Plain GPTQ (notebook 02)

Beats RTN on C4, the text it was calibrated on, but loses on WikiText2: it fits the calibration text too closely.

Layer by layer · 12 layers checked

On calibration-like inputs GPTQ's layer error is below RTN's on all 12 layers, up to 250× lower. On unseen WikiText2 inputs the gain shrinks, and one layer (block 5 down-proj) is worse than RTN.

Act-order + static groups

Rounds the most important columns first. Beats RTN on both datasets: 10.19 vs 10.74 and 16.28 vs 17.23.

Results · notebooks 02 and 02b · full layer table in Backup E12
On Qwen, plain GPTQ from notebook 02 was a surprise: worse than RTN on WikiText2, 11.18 versus 10.74. The diagnostic explains it. On C4, the same kind of text it was calibrated on, plain GPTQ does beat RTN, 16.64 versus 17.23. So it fits its calibration text too closely and generalizes less well. Layer by layer, on inputs like the calibration text, GPTQ's error is below RTN's on all 12 layers I checked, up to 250 times lower, but the gain shrinks on unseen WikiText2 inputs, and one MLP layer in block 5 is actually worse than RTN. The fix is GPTQ's standard option, act-order, which rounds the most important columns first, combined with static groups so the grid stays exactly RTN's. That beats RTN on both datasets: 10.19 versus 10.74, and 16.28 versus 17.23. Adding true-sequential gave no further gain. This is the GPTQ setting I plan to compare against RTN in the exams.
